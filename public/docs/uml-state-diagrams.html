3. Equipment deploy status

Transitions are not enforced server-side — admin or crew can change to any value directly. This is the expected operational path.

stateDiagram-v2
    direction TB

    [*] --> na : equipment created

    na --> deployed : crew installs
    na --> not_needed : cut before deploy

    deployed --> done : show wraps
    deployed --> returned : pulled early
    deployed --> damaged : gear fails

    damaged --> returned : after teardown
    done --> returned : checked back in

    returned --> [*]
    not_needed --> [*]

    note right of na : gray badge
    note right of deployed : yellow badge
    note right of done : green badge
    note right of returned : blue badge
    note right of not_needed : red badge
    note right of damaged : purple badge

When Project.returnPhaseActive is true, crew see done gear surfaced as Return tasks in /tasks alongside the existing Deploy tasks (anything still na). The deploy-status field itself is unchanged — the toggle only decides which states the task list pulls.

5a. Panel Studio session mode

Same route (/projects/[id]/panel/[equipmentId]) renders in different modes depending on who is viewing, who the panel belongs to, and how the operator arrived. Mode determines whether save is direct (admin) vs change-request (everyone else), whether Copy/Paste appears, whether the Browse Header sits above the chassis, and whether per-key Approve/Deny toggles render.

stateDiagram-v2
    direction TB

    [*] --> own_panel : Viewer = panel's assigned member
    [*] --> others_panel : Viewer != assigned member\n(admin manager global admin only)

    own_panel --> own_admin_direct : Viewer is admin
    own_panel --> own_request : Viewer is manager crew user

    others_panel --> others_admin_direct : Viewer is admin (global or scoped)
    others_panel --> others_request : Viewer is manager (sends as endorsement)

    own_admin_direct --> browse_layer : URL has ?from=my-equipment
    others_admin_direct --> browse_layer : URL has ?from=my-equipment
    others_request --> browse_layer : URL has ?from=my-equipment

    browse_layer --> review_mode : URL has ?review=memberId\n(admin clicked Review in Tasks)

    review_mode --> applied : Admin Resolves with at least one approval
    review_mode --> rejected : Admin Resolves with all denied
    applied --> [*] : router.replace /admin
    rejected --> [*] : router.replace /admin

    note right of own_admin_direct : Edit then saved immediately. No change-request. Copy + Paste hidden.
    note right of others_admin_direct : Edit then saved immediately (global admin override). Copy + Paste shown. Browse Header above if ?from=my-equipment.
    note right of own_request : Edit then ChangeRequest(submitted). Green highlight on key. No Copy/Paste.
    note right of others_request : Edit then ChangeRequest(submitted) marked mgr_endorsed if viewer is manager. Copy + Paste shown.
    note right of browse_layer : Adds Browse Header: show user chevrons. Nav highlight flips to My Equipment. Cookies remember last project and member.
    note right of review_mode : Per-key Approve/Deny toggles replace picker. Resolve button replaces Save. Submitted-green keys read-only until per-key choice made.

Mode-determining inputs

InputSource
Is panel mine?equipment.assignedToId === session.member.id
Am I admin?session.memberships.some(m => m.role === 'admin') (global) OR currentMembership.role === 'admin'
Am I manager on this project?currentMembership.role === 'manager'
Browse mode?URL ?from=my-equipment is present
Review mode?URL ?review={memberId} is present (only admin gets the route here from Tasks)

6a. RackSlot lifecycle (Rack Studio, v2.4)

The slot moves through a small state machine driven by drag-and-tap operator actions. Library tiles + chassis rows act together as the placement target. A slot can be linked to an Equipment row (equipmentId IS NOT NULL) or stand-alone — the link is set at creation and can be swapped via the slot's edit form, but the slot itself stays the same row.

stateDiagram-v2
    direction LR

    [*] --> picked : Operator drags a library tile\nOR taps a free RU then a tile

    picked --> placed : Drop on free RU range\n(server collision check passes)
    picked --> [*] : Drop outside chassis\nOR drop on occupied range (snap-back)

    placed --> placed_repositioned : Operator drags slot card to a new RU\n(server collision check passes)
    placed --> placed : Operator edits label deviceType ruSize\n(same row different fields)
    placed --> placed : Operator swaps equipmentId\n(linked slot variant only)
    placed --> [*] : Operator deletes slot (confirm modal)

    placed_repositioned --> placed : (alias - same DB state)

    note right of picked : Client-only ghost state. No DB row yet. pendingDragRef OR armedRu set in client.
    note right of placed : RackSlot row exists in DB. Visual: card on the chassis with label, RU numbers stacked in cyan, deploy badge if linked to Equipment.

Linked vs unlinked slot variants

stateDiagram-v2
    direction LR

    [*] --> unlinked : Slot created from a generic preset\n(deviceType from library, label hand-entered)

    unlinked --> linked : Slot edit form picks an Equipment row
    linked --> unlinked : Slot edit form picks "no equipment"
    linked --> linked : Swap to another Equipment\n(same category same rack only)

    note right of unlinked : equipmentId=null. Slot label is hand-typed. Renders as plain card.
    note right of linked : equipmentId points at Equipment row. Label uses equipment.name. Card surfaces equipment.location (cyan), hardwareType (gray), deploy status badge, IP (cyan link on screen).

6b. RackTemplate department (Rack Studio, v2.4)

RackTemplate.dept decides which side of the company the rack belongs to — affects library default category filter, which presets show up, and where the rack is grouped on the Racks tab. Today the Racks tab is only Comms-scoped — radios dept is reserved for the future Radio rack designer.

stateDiagram-v2
    direction LR

    [*] --> comms : Created from the Comms project Racks tab (default)
    [*] --> radios : Created from a radio-focused workflow (field set explicitly)

    comms --> comms : (no transitions in current build)
    radios --> radios : (no transitions in current build)

No UI to flip dept after creation; if you need to move a rack between departments, delete + recreate.

7. SwitchPort visual state (Switch Studio, v2.5)

Each port on a switch's chassis has one of three visual states. Plus an orthogonal Trunk flag that overrides the cell color (gray + T badge) while preserving the underlying profile assignment.

stateDiagram-v2
    direction LR

    [*] --> unseeded : Equipment created
    unseeded --> assigned : First Switch Studio open\n(lazy-seed defaultFor(portIndex, kind))
    unseeded --> unassigned : (rare - defaultFor returns vlanId=null)

    assigned --> unassigned : User picks "Unassign"
    unassigned --> assigned : User picks any profile
    assigned --> assigned : User picks a different profile

    note right of unseeded : No SwitchPort row exists. Loader detects 0 rows and seeds. Invisible to user.
    note right of unassigned : profileId=null + isTrunk=false. Empty outlined cell with em-dash centered.
    note right of assigned : profileId points at VlanProfile row. Cell filled with profile.color, port number small at top, VLAN ID centered.

Trunk flag (orthogonal)

stateDiagram-v2
    direction LR

    [*] --> not_trunk
    not_trunk --> trunk : User toggles Trunk on
    trunk --> not_trunk : User toggles Trunk off

    note right of not_trunk : isTrunk=false. Cell renders using profile.color (or empty if profileId null).
    note right of trunk : isTrunk=true. Cell renders gray (Management color) regardless of underlying profile. White T badge bottom-right. profileId preserved.

Trunk is independent of profile assignment — a trunk port still has a "primary" VLAN at the hardware layer, but the chassis at-a-glance reads better when every trunk is uniformly gray (matches NETGEAR ProAV Engage UI). Toggling Trunk off restores the colored fill without re-picking the profile.
